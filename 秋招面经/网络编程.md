一般来说提到网络编程指的都是linux下的网络编程，因此后续以此为背景，回顾所学知识的同时会在末尾增加一些遇到的面经和对应的答案
## 套接字socket

- 创建一个服务器的起手几步一般都是先创建一个监听套接字，套接字可以理解为一根管道，用于连接服务器和客户端，数据就在其中传输。以cpp为例，常用库有：sys/types.h、sys/socket.h、netinet/in.h、arpa/inet.h等
普通的套接字调用
```socket(int domain, int type, int proto)```
 即可创建，三个参数说明如下：domain是地址族，常用的如ipv4、ipv6、unix域套接字；type是类型，一般来说tcp用sock_stream（字节流），udp用sock_dgram（数据报）；proto一般填0即可，默认协议。
 
 
- 创建套接字后服务端还需要绑定到本机的ip:port上，然后开始监听连接，绑定使用
```bind(int sockfd, const struc sockaddr *addr, socklen_t len)```
函数，bind需要传入的参数第二项是ip:port的描述，通过sockaddr_in这个结构体来描述地址结构，里面主要三个字段sin_family表示地址族，sin_port表示端口，sin_addr.s_addr表示地址，一般使用ipv4下，地址族使用af_inet，地址使用inaddr_any来表示监听本机所有接口，当然也可以使用127.0.0.1回环地址表示用于只监听本机，而填写端口号时，一般还需要调用一下 htons() 函数，用于大小端序的转换。此外也顺便提一嘴，地址的转换使用inet_pton(int af, const char* src, void* dst)，af是地址族，src是原字符串的地址，dst是转换后的二进制地址。
完成地址描述结构体的填充后就可以调用bind进行绑定了，sockfd就是前面创建socket创建出来的fd，之所以是fd（文件描述符）的原因是，linux的思想就是一切皆文件，设备是文件，套接字当然也能是文件，这样就可以忽略其底层的网络细节而将其当作一个文件一样进行读写的操作。传入addr时则需要做一下强转，转成参数中需要的sockaddr结构体指针类型，函数这样的设计和前面构造结构体的使用方式是有原因的，因为bind不是专为ipv4进行服务的，因此要求传入的sockaddr其实更像是一个基类，而使用时可以使用实际需要的子类构造地址信息，然而我们知道c中是没有父子类和继承的概念的，其实库底层结构体定义是通过直接预留空间来实现，子类通过填充来满足结构体大小。len则是地址结构体的大小。
- 绑定后接下来要把fd设置为监听状态，设置后就得到了我们常说的监听fd。使用函数
```listen(int fd, int backlog)```
其中fd是我们要监听的目标fd，backlog的参数含义则是已建立连接的队列的大小，在tcp的三次握手中，客户端一般是主动连接的一端，而服务器是接受连接的一方，当收到syn并返回syn+ack时，这个时候的连接被称为是半连接，半连接队列的大小可以在内核的配置文件中修改，收到客户端的ack后，三次握手结束，这个时候才进入全连接队列。这个全连接队列不意味着可以直接使用其中的连接fd，因为内核并不知道此时用户态是否想处理连接，也不知道是否有空闲线程来处理新连接，因此还需要下一步的accept操作
- accept函数的作用就是从全连接队列中取一个连接出来并返回新的fd，原型
```int accept(int fd, struct sockaddr* addr, socklen_t* addrlen)```
参数fd就是监听socket的fd，后面两个参数一般用于保存连上的客户端的地址信息，一般可以忽略（如果业务无需使用相关信息的话）。函数的返回值就是新建的连接socket的fd。后续和这个客户端的通信就可以通过操作这个fd来实现。
- 前文的操作都是服务器相关的，接下来看下客户端的视角。实际上服务器本身也可以作为客户端连接别的服务器，也就是所谓的服务间通信，实际当然会更复杂一些，可能使用如Kafka、NATS之类的中间件。
```int connect(int sockfd, const struct sockaddr* addr, socklen_t addrlen)```
这个是连接函数的原型，sockfd就是客户端的socket，后面的参数是服务器的地址描述，返回值0表示成功，-1表示失败，connect的底层就是通过发起三次握手和服务器建立tcp连接。

## IO多路复用

前面的socket是网络编程的基础，接下来的IO多路复用则是实际工程的实现和应用的核心
对于每个监听socket（后文统称listen socket），如果每到来一个新的连接socket（后文统称connect socket）都创建一个进程/线程来监听处理，那么整个系统的开销将会快速的上涨，并且如果有一万个连接，分配一万个线程也是不现实的，内存和cpu根本没能力处理这一万个连接的并发。而IO多路复用就是为了实现通过单个线程来同时监听多个fd。
常见的IO多路复用有三种：select、poll、epoll

 - 先说明一下关于阻塞IO和非阻塞IO的定义，以read读取调用为例，阻塞IO当缓冲区没有数据时，cpu会空转占用等待数据到来，而非阻塞IO在缓冲区没有数据时则会直接返回同时设置errno。一般使用IO多路复用时都会把fd设置为非阻塞的，防止出现一个fd卡住整个线程的情况，通过fcntl函数设置其flag为O_NONBLOCK即可
 - select：原理是在用户态下构造需要监听的fd的位图，然后传给内核，内核会先检查一遍是否就绪，没有的话就将进程挂起到等待队列上，进程将会睡眠，某个fd状态变化时内核会唤醒等待的进程，并重新遍历fd集合检查哪些fd就绪，将就绪结果写入输出位图复制回用户态。在用户态视角下，传入的位图是标记要监听的fd，返回的位图是就绪的fd。
select的最大优势在于其可移植性、轻量且逻辑简单易使用、超时精度高，但是也有很大的局限性，首先就是其位图大小为1024，导致了能监听的最大fd编号和数量为1024，其次就是每次调用需要将位图拷进内核，内核在检查时都需要遍历，取出返回用户态后用户态也需要遍历处理，不过实际上select也不会每次都遍历1024个位置，只会遍历到传入的最大fd+1的位置，因此如果是监听的fd稀疏的情况下，会有更大的额外开销
- poll：原理和select类似，但是将通过位图记录要监听的fd改成了通过数组记录，这样就实现了1024的上限的突破，同时可以按需加入fd而省去了无用的遍历检查。但并没有本质解决问题，一个fd的就绪还是会导致整个数组的遍历来确定哪些fd就绪。
相比于select，poll的适配性更多是类unix系统广泛支持。
- epoll：来到重头戏了，epoll是linux网络编程最常用常见的IO多路复用，解决了select和poll的遍历的主要问题，是高并发的基础
epoll记录监听的fd的方式是内核维护的一个红黑树，epoll有三个函数：epollcreate，epollctl，epollwait。
epollcreate就是创建一个epoll实例红黑树，后续通过epollctl向这个实例中注册要监听的fd，会插入到红黑树中，调用epollwait就是从就绪队列中取出就绪fd，如果就绪队列为空线程就会休眠，内核会将其挂在对应epoll实例的等待队列上，当有注册的fd就绪时，epoll会将其挂到就绪队列中并唤醒等待的线程，线程苏醒运行后会从就绪队列中取fd出来处理。注意上述过程中fd就绪和取出都不用遍历已注册的所有fd，这极大减少了时间开销。
epoll的fd可以设置其触发方式，有ET和LT两种选项，LT就是水平触发，当注册的fd就绪时就会一直通知，ET则是边缘触发，只会在fd就绪时通知一次。以读事件为例，当缓冲区有数据可读时，LT就会一直提醒，而ET只会提醒一次，如果这一次处理没有读完缓冲区的所有数据，剩余的数据也不会再触发fd，只能等待下一次有新数据到来才会触发。
除此之外fd还可以设置EXCLUSIVE和ONESHOT属性，二者分别用于处理惊群和并发问题。EXCLUSIVE会在一个fd注册到了多个epoll实例时，设置了该属性的fd就绪只唤醒其中的一个epoll实例；而ONESHOT则是会在一个fd就绪触发后临时的将这个fd禁用，不再继续上报任何事件，防止在处理该fd时，又有新数据到来其又触发一次，被其他线程也取走处理，导致两个甚至多个线程对一个fd进行IO的情况，需要注意的是，ONESHOT的fd在触发处理完后需要重新设置监听。
反直觉的一点是，epoll中其实并不允许EXCLUSIVE和ONESHOT两个属性同时使用，也就是说很难只通过设置属性来同时避免惊群和并发问题，那么就可以从架构设计入手来实现多线程高并发下的IO多路复用与业务处理。
## Reactor
reactor是常见的一种同步IO的服务器架构，最简单的设计如下：
单线程创建listen socket和一个epoll fd，并将listen socket注册到epoll中，并循环调用epollwait来获取就绪事件，当就绪fd就是listen socket本身时，说明有新连接到来，通过accept取出并注册这个新的connect socket到epoll中；当就绪fd不是listen socket时，说明是connect socket中有事件，做完IO后将数据再根据对应的handler进行处理即可。
这是一个单线程监听、单线程IO、单线程处理业务的一个模型
现在进一步扩展，通过多线程来处理连接、IO与业务。一般会使用叫做主从Reactor的模型：
首先，一个线程只持有一个listen socket和一个epoll实例，这个实例中只注册listen socket的fd，该线程被称为Mainreactor，只负责监听新建的连接，并将connect socket分发给Subreactor，这里可以通过哈希或者随机轮询的方式进行负载均衡。
被分发到的Subreactor会将这个fd注册到自己的epoll实例中，对于一个fd来说，其同时只会在一个Subreactor的epoll中存在，这样就保证了每次触发也只会有这个线程来处理它的相关IO。这其中fd的传递可以有很多方式，如安全的生产者消费者队列等等，其中比较有意思的一个方式是向Subreactor在监听的一个fd中写入传递的fd，这样Subreactor就会在wait后发现这个fd有个可读事件，然后再取出fd并创建监听对象、注册该fd到自己的epoll中，当然也不一定要通过这个fd来传递新fd本身，其也可以作为一个通知告诉Subreactor队列中有fd了需要取出处理
拿到connect socket的子线程可以自己做业务逻辑的处理，也可以进一步的派发到工作线程池。
一般来说如果工作线程操作数据时会改变这个数据，则需要对这个fd上的任务做串行处理，确保不会因为多线程下并发执行导致的数据冲突。更方便的方法是直接每个Subreactor再配套一个工作线程，Subreactor只负责IO，业务交给工作线程处理
